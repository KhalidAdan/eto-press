This section is for the second reader of these docs: not the editor setting
up a paper, but the developer who wants to know how the machine works. It
assumes you have the repository open.

## The monorepo

<FileTree>
- packages
  - platform — the machinery of a personal periodical; knows nothing of news
  - engine-eto — the flagship doctrine: prefilter, judge, cluster, composite, the cage
  - engine-desk — the null engine: the editor writes, the press prints
  - engine-letter — watch an institution's doors; print when one speaks
  - engine-digest — a reading list per section, no retelling
  - engine-sports — signed columns from the desk, then a link list per league
  - engine-wrap — labeled figures and their motion since the last edition
  - press — the thin binding: preflight, the joint, the tail, the verb shims
  - cli — the `eto` command; each verb loads a press module via tsx
  - subscribe — the double-opt-in edge functions
- docs — the design documents (North Star, pipeline, roadmap, experiments)
- docs-site — this site
</FileTree>

**The dependency arrows point one way.** Engines import the platform; the
press imports both; the platform imports nothing above itself. There is no
way to express "the platform calls the engine's clustering" — the only
crossing is the joint.

## The joint

One call per morning:

```ts
// packages/platform/src/engine.ts
interface Engine<E, R> {
  name: string
  doctrine: ReadonlyArray<string>   // printable principles
  models: ReadonlyArray<string>     // non-empty = preflight pins; [] = no Ollama needed
  edition: (day: Day) => Effect<EngineOutcome, E, R>
}

type Day = { runId: string; masthead: Masthead }   // no corpus — engines build their own

type EngineOutcome =
  | { _tag: "Edition"; stories; report; advisoryLines }
  | { _tag: "NoEdition"; reason: string }           // no file, no mail, one honest note
```

`packages/press/src/run.ts` is the frame: preflight (masthead, migrations,
model pins), the joint, then the tail — pending corrections spliced in, the
markdown dialect rendered, the atomic archive write, and the
published-edition store written right after it. The site, email, and RSS
dialects are separate verbs that read the store. `main.ts` holds the static
engine registry — eto, desk, letter, digest, sports, wrap — picked by
`eto.toml [engine] use`.

`engine.models` only gates: a non-empty list means preflight asks the
inference provider to pin. What gets pinned is the provider's configured
models, each with the strongest identity the provider can promise (Ollama:
a content digest). A null digest is logged as unpinnable and never written
to `models.lock.json`.

The interface is deliberately **private to the monorepo**: six engines
consume it, and interfaces drawn from n=1 are reliably wrong, so it stays
unpublished until the contract has settled across those consumers.

## Effect, everywhere

The codebase speaks [Effect](https://effect.website): every stage is an
`Effect` with its failure types in its signature, retry policies are
`Schedule` values owned by the stage, and external services — HTTP, SQLite,
the inference boundary, the Desk — are Layers. That last part is the
architecture's honesty mechanism: an engine's requirements are visible in
its type, and `main.ts` names the ceiling on what any engine may require —
the SQL client, the HTTP client, the inference service, and the Desk. Ollama
is provided to the inference service and appears nowhere in that ceiling;
the filesystem is the frame's, for the archive and the lock file, and no
engine's. The services an engine is never handed (the filesystem, the model
server, the archive, the mail) are simply absent from what the press
provides it, and the type refuses an engine that asks. The test suites swap
the same Layers for fakes, which is how failure paths run without a GPU or
a network.

## Reading order

1. `packages/press/src/run.ts` — the frame; the whole morning in one file.
2. `packages/engine-eto/src/engine.ts` — stages 1–9 behind the joint.
3. `packages/platform/src/inference.ts` — the closed set of questions a
   stage may ask a model; `inference-ollama.ts` — the one provider that
   answers them, where the prompts and parsers live.
4. `packages/platform/src/edition.ts` — the document every dialect consumes.
5. `packages/platform/src/render.ts`, `published.ts`, `html.ts` — the
   markdown dialect, the store, the site.
6. `packages/engine-desk/src/engine.ts` — the whole engine idea in ~110
   lines; the best single file for understanding the boundary.
